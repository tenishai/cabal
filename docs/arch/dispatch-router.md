# dispatch-router — the one place every Task hop goes through

WHAT / SEAM: `DispatchRouter` (core/broker/router.py). `dispatch(target_agent, target_generation, task, caller_jwt) -> Task`, `start_detached(...)` (start phase now, run phase returned as a coroutine for the app's `DetachedTasks`; cabal#277), `dispatch_streaming(...)` (text deltas), `resume_local(...)`, `schedule(...)` (cabal issue 406: checks the caller and target now, then writes a `scheduled` conversations row with the caller's claims and no token; core/scheduler.py starts it later through `start_detached(scheduled=True)`). Registry: `register_local(LocalHandler)`, `register_capabilities`, `select_by_capabilities` (first superset match, sorted by name). Errors: `DispatchError` ⊃ `AgentNotFoundError`, `GuardrailBlocked`, `DrainingError`, `TaskAlreadyRunning`, `CallerJWTError`, `ConfigurationError`. `running` is the `RunningTasks` registry (core/running.py; cabal issue 405): the dispatches running now, plus the drain flag. Built once in core/app.py lifespan → `app.state.dispatch_router`.
OPS / FLOW: `dispatch` = `_start_dispatch` + `_run_dispatch`. Start: `_prepare` (bulletin lookup: active row, or pinned generation; verify caller JWT against JWKS with expected aud = target name, or `federation_audience` for kind=federated; revocation check) → `_refuse_not_before` (a `cabal_not_before` in task metadata is refused unless `scheduled`, so a door that can't schedule never silently starts at once) → `_admit` (while draining, refuse with DrainingError unless the caller's sub names an agent that is itself the target of a running task) → `_ensure_trace` → `_track` (onto `running`; an id already listed is refused as `TaskAlreadyRunning`, 409 on /a2a/tasks and on resume, before anything is written; removed again if the rest of the start raises). Every remover, `DetachedTasks._finished` included (it notes the entry at `spawn`), passes the entry it added, so a refused duplicate on any path, streaming and resume included, never unlists the run holding the id) → AbortCoordinator.register → `Bookkeeper.on_dispatch_start` → SESSION_START hook (session root only). Run: router input guardrails (PASS / BLOCK→policy-violation Task / REWRITE→replace Task / TERMINATE→raise GuardrailBlocked) → local handler if registered and kind≠federated, else HTTP POST `<endpoint>/a2a/tasks` with the caller JWT → `on_dispatch_working` just before the persona call → `handle_waiting` (broker/waiting.py, cabal issue 406: a reason-705 reply with `cabal_waiting.until` gets a continuation scheduled in the same contextId under `_Started.caller_claims` and reads completed; without `until`, claims or a valid time, with `until` past the caller's token `exp`, past `max_wait_continuations`, or when scheduling fails, it reads input-required; the continuation keeps `cabal_delegation_depth` and `cabal_trace_id`) → bookkeeping success/failure (reply stored via `_with_context`: contextId and history kept for ListTasks/context replay, cabal#276) → SESSION_END hook. Every path takes the task off `running` in a `finally` that runs after the success bookkeeping and SESSION_END: `_run_dispatch` (around `_run_dispatch_body`), the `dispatch_streaming` wrapper around `_stream` (so a dropped stream is removed too), `resume_local`, and `DetachedTasks._finished` for a detached run cancelled before it started.
INVARIANTS (docstring §6.12; the numbering is the codebase's):
- (2) Caller JWT verified on EVERY dispatch, in-process included. WHY: the doors re-mint, the router is the check; do not add a local fast path that skips `_prepare`.
- (3) Bookkeeping on every dispatch; failure recorded ONCE. WHY: the non-streaming TERMINATE raise sits inside the try whose `except` already calls on_dispatch_failure; adding another call double-writes events (cabal#152 comment in `dispatch`).
- (4) `cabal_trace_id` kept if present, fresh `cabal_span_id` per hop, in task.metadata.
- (1) AgentCard signature verification is NOT enforced: nothing calls `AgentCardVerifier` (core/a2a/card.py). The JWT is the trust (#226). STATUS.md is a historical record; its banner and invariants table both say the verifier has no caller on the dispatch path.
- The running list is the in-process registry, never the `conversations` rows: a row stays `working` if the success bookkeeping raises. The drain's busy-caller check uses the verified JWT sub and `running`, never task metadata such as `cabal_parent_task` (inbound strips `cabal_*` since PR 402, and the rule must not depend on that). The task is listed from `_admit` until its result is written and SESSION_END has fired, so an empty list means nothing is left to lose. A refused dispatch writes no row: `_admit` runs before `on_dispatch_start`.
- DrainingError maps to "retry later": 503 + Retry-After on /a2a/tasks, ERROR_DRAINING (-32004) on JSON-RPC, UnsupportedOperation on v1. Like GuardrailBlocked, every caller catches it BEFORE DispatchError.
- GuardrailBlocked must map to 403 / ERROR_FORBIDDEN, never 502 / ERROR_INTERNAL. WHY: clients retry server faults, which feeds the loop the guardrail exists to break. Every caller (routes/tasks.py, a2a_jsonrpc `_message_send`, a2a_v1) catches it BEFORE DispatchError; a new caller must too.
- Federated rows always go remote even if a local handler exists (persona_factory registers one for every identity.toml persona). The mint site (`_dispatch_auth.dispatch_token`, which takes the audience from `dispatch_audience`) always resolves the ACTIVE row, but `_prepare` resolves the pinned row when the caller passes `target_generation` (caller-controlled, e.g. POST /a2a/tasks). The two can disagree; what keeps that fail-closed is `_prepare`'s own aud check against its row (a mismatch is a 401 CallerJWTError). Keep the router's aud check if you change audience resolution.
- Router guardrails are ONE shared instance set (doom-loop, delegation depth/budget/edges; built by app.build_router_input_guardrails). Personas get the router's budget via `input_guardrail_of(DelegationBudgetGuardrail)`. WHY: a second instance doubles a conversation's delegation allowance.
- A role="primus" persona registers as `<name>-primus`; an unpinned miss suggests the suffix.
CONSUMERS: routes/tasks.py, routes/a2a_jsonrpc.py (message/send, message/stream, tasks/get), routes/a2a_v1.py (v1.0 SendMessage; `start_detached` for returnImmediately), routes/admin.py (resume, abort, graph, persona graduate, reload/identity; `running` for GET /admin/tasks/running and POST /admin/drain[/cancel]), routes/healthz.py (`draining`), core/detached.py (removes a finished detached run from `running`), tui/client/inprocess.py, core/persona_factory.py (registration, shared abort/guards), agents/primus.py (shares the router's budget guard; its fan-out legs call Subordinates directly, NOT through the router).
